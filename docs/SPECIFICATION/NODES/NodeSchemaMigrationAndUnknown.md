# ノードスキーマ移行とUnknownNode復旧

## 状態

SchemaVersion、移行、バックアップ、失敗時プレースホルダーおよび復旧時期は確定。

## バージョン

- すべてのノード型の初期 `SchemaVersion` は整数 `1` とする。
- バージョンを飛ばす移行は行わず、`vN -> vN+1` の `INodeStateMigrator` を順番に適用する。
- `NodeTypeId` と移行元・移行先バージョンの組み合わせは一意でなければならない。

## 移行とバックアップ

- プロジェクト状態を変更する移行前に、プロジェクトマニフェストのタイムスタンプ付きバックアップを作る。
- バックアップはプロジェクト内 `Backups` に保持し、最新5世代を残す。
- 全移行はメモリ上のコピーへ適用し、成功後にだけ実行状態へ採用する。
- 移行後はプロジェクトをDirtyにするが、自動保存しない。

## UnknownNode

- 共通プレースホルダー型IDは `system.unknown_node` とする。
- 型未登録、現在より新しいSchemaVersion、または状態移行失敗を `UnknownNode` として扱う。
- `OriginalNodeTypeId`、SchemaVersion、生状態、保存済みポート、接続、位置および共通状態を保持する。
- ポート定義がない旧データでは、接続端点IDから型不明・接続不可のスタブポートを再構成する。
- `UnknownNode` は追加メニューへ表示せず評価しない。

## 復旧

- プロジェクト読込時に対応型が利用可能なら、自動的に移行と復元を試みる。
- 開いているプロジェクトでは、ユーザーの `Try Restore` 操作で個別または一括復旧を試せる。
- 復旧はメモリ上で検証し、成功したノードだけ置き換える。
- 失敗時は元の `UnknownNode` データを変更しない。

## 設計意図

- 新旧バージョン差や欠落型があっても、プロジェクト全体を開けるようにする。
- 失敗した移行で元データを上書きしない。
- 復旧可能な情報をプレースホルダーへ残す。
