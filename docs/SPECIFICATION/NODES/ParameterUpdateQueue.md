# パラメーター更新キュー

## 状態

複数更新の優先規則、スレッド境界、キュー上限およびプロジェクト読込時クランプの扱いは確定。

## 更新順序

- UI、カスタムUI、プリセットおよび物理入力のイベントは、入力ルーターで単調増加する `SequenceNumber` を受け取る。
- バックグラウンドスレッドからのイベントはスレッドセーフなキューへ投入し、ノード状態を直接変更しない。
- グラフを評価するメインスレッドが、評価フレーム境界でキューを1回だけ切り離して処理する。
- キュー切り離し後に届いたイベントは次の評価フレームへ送る。
- 同じパラメーターへ複数の `BaseValue` 更新がある場合、検証に成功した最大の `SequenceNumber` を採用する。
- プリセット内の全更新は同じトランザクションIDを持ち、部分適用しない。
- 更新確定後に全 `EffectiveValue` を1回計算してからノード評価を開始する。

## 負荷制御

- 同じ `Value` 論理コントロールの連続更新は、キュー内で最新値へ合流できる。
- 同じUI編集操作からの連続更新も、未処理なら最新値へ合流できる。
- プリセットトランザクションと `PresetTrigger` 発火は合流せず、順序を保持する。
- 1フレームで処理する非合流コマンドの上限は4096件とする。
- 上限を超えた新規コマンドは受理せず、操作画面と診断履歴へ過負荷エラーを出す。
- 受理済みコマンドを黙って破棄しない。

## 共通API

- 値変更は `TryEnqueueBaseValueChange(NodeInstanceId, ParameterId, Value, Source)` に相当する共通APIへ集約する。
- APIは対象、型、有限値および参照の検証を行い、範囲超過だけはクランプする。
- 変更イベントはフレーム境界で値が確定した後に1回通知し、要求投入時には通知しない。
- カスタムUIとプリセットも同じAPIを使用する。

## 読込時補正

- 旧保存値が現在のハード範囲外なら、読込時にクランプして警告を1回表示する。
- 読込時に補正したプロジェクトはDirty状態にするが、自動保存しない。
- ユーザーが保存したときだけ補正後の値を永続化する。

## 設計意図

- スレッドやイベント到着順によって同一フレームの映像が変わることを防ぐ。
- 高頻度入力を合流しながら、プリセットの原子性と順序を維持する。
- 読込だけでユーザーのプロジェクトファイルを書き換えない。
